Own UI widget identity, draft/accepted values, explicit handlers, revision-safe events, atomic updates and compatible source-model replacement inside an embedding application.

## Ownership and implementation

`SDUI/go/runtime` provides `Session`, typed handles/events and updates. `reload` prepares source candidates; publication belongs to the host. There is no runtime daemon or standalone runtime process: `EmbeddingApplication` is context supplied by a host. An independently packaged runtime library and optional executable shell are target boundaries.

The system owns the modeled core and its internal units. `HostEventAdapter` is a
context participant, not an additional deployed product. `EmbeddingApplication` represents
the actual embedding process role; it is not a new binary created by this model.
Shared package boundaries and extraction targets are separate from current process
deployment. [Ecosystem coverage](../README.md) records the combined entrypoints.

## Public boundary and scenarios

The scenario describes a string-valued input commit. Actual `runtime.Event` also includes session identity, widget kind and event kind; typed values support string and boolean. The model fields are a scoped channel projection, not an ABI declaration. `Dispatch` invokes only a handler installed by `Bind`. The handler returns updates, and the session validates/publishes them atomically. Host goroutine ownership is required.

`DispatchUiEventAccepted` and `DispatchUiEventRejectedScenario` describe the successful and
rejected logical call paths. The success result projection includes diagnostics; the rejection message has a
separate diagnostic-only contract and no generated/model/presentation payload. These named messages/channels
are analysis projections of Go calls, not shipped RPC names or wire contracts.
The closed contracts close only this deliberately bounded projection. They do
not claim all implementation fields or every interaction have been modeled.
Modes name operational contexts and do not implement a state machine.

## Limits and unresolved packaging

The runtime stores no native widget pointers, owns no Go domain state and does not execute SDL. `SDL/go/bridge` validates explicit plans against loaded SDL runtimes, then registers Go handlers; that adapter belongs to SDL integration, not this system. No C ABI, remote session protocol or arbitrary callback loading is implemented.

Dedicated binary naming, installation and independently versioned library releases
remain extraction decisions. SDPTool can orchestrate public CLI or Go library
entrypoints; this model does not add a dependency or claim all integrations exist.

## Validate and browse

From the repository root:

```sh
go -C SDL/go run ./cmd/sdl check ../../SDP/SDL/SDUI/SDUIRuntime/System.design
go -C SDL/go run ./cmd/sdl ast ../../SDP/SDL/SDUI/SDUIRuntime/System.design
go -C SDL/go run ./cmd/sdl viewpoints ../../SDP/SDL/SDUI/SDUIRuntime/System.design --format static --output /tmp/sdp-sdui-sduiruntime
```

The single entry is independent; no import, source-set registration or implicit
folder namespace is assumed. Output is generated by SDL tools, never authored by
hand. Parser success validates this model, not native/runtime behavior. Model
navigation registration in SDPTool remains explicit; merely adding this folder
does not install a navigation project.
