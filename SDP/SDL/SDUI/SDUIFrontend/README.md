Parse SDUI 0.2 into a source-positioned AST, validate the local language profile and normalize reusable definitions to instance trees.

## Ownership and implementation

`SDUI/go/parser` is the reusable Go library. `SDUI/go/cmd/sdui` currently combines parsing with presentation exports; there is no separately packaged frontend executable. `parser.Parse`, `Validate`, `Normalize` and `Compile` are actual entry points.

The system owns the modeled core and its internal units. `SourceCaller` is a
context participant, not an additional deployed product. `SduiCommand` represents
the actual embedding process role; it is not a new binary created by this model.
Shared package boundaries and extraction targets are separate from current process
deployment. [Ecosystem coverage](../README.md) records the combined entrypoints.

## Public boundary and scenarios

The source string and entry selector are logical invocation inputs. `Compile` returns a document and map of roots; selecting an entry belongs to the caller. `ModelProjection` summarizes these Go objects and is not an implemented serialized instance ABI. Syntax-only AST output is explicitly weaker than full local-profile validation.

`CompileUiAccepted` and `CompileUiRejectedScenario` describe the successful and
rejected logical call paths. The success result projection includes diagnostics; the rejection message has a
separate diagnostic-only contract and no generated/model/presentation payload. These named messages/channels
are analysis projections of Go calls, not shipped RPC names or wire contracts.
The closed contracts close only this deliberately bounded projection. They do
not claim all implementation fields or every interaction have been modeled.
Modes name operational contexts and do not implement a state machine.

## Limits and unresolved packaging

The parser does not open `ref` sources, call callbacks, resolve SDL action modules or run Go. Named frames/groups, regions, formatting and symbolic connections are supported. Scroll layout is rejected. A future dedicated executable/library packaging boundary must preserve these semantics.

Dedicated binary naming, installation and independently versioned library releases
remain extraction decisions. SDPTool can orchestrate public CLI or Go library
entrypoints; this model does not add a dependency or claim all integrations exist.

## Validate and browse

From the repository root:

```sh
go -C SDL/go run ./cmd/sdl check ../../SDP/SDL/SDUI/SDUIFrontend/System.design
go -C SDL/go run ./cmd/sdl ast ../../SDP/SDL/SDUI/SDUIFrontend/System.design
go -C SDL/go run ./cmd/sdl viewpoints ../../SDP/SDL/SDUI/SDUIFrontend/System.design --format static --output /tmp/sdp-sdui-sduifrontend
```

The single entry is independent; no import, source-set registration or implicit
folder namespace is assumed. Output is generated by SDL tools, never authored by
hand. Parser success validates this model, not native/runtime behavior. Model
navigation registration in SDPTool remains explicit; merely adding this folder
does not install a navigation project.
