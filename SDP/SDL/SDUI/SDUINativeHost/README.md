Provide an interactive desktop container that translates native Fyne input to SDUI session operations and renders current snapshots using the shared geometry engine.

## Ownership and implementation

The `sdui-fyne` executable exists under the `desktop` build tag. `SDUI/go/host/fynehost` is its reusable native adapter. SDL bound demos reuse this adapter from separate combined applications. Fyne is an actual dependency; FOX and an SDUI TUI are not implemented host backends.

The system owns the modeled core and its internal units. `UserInputSource` is a
context participant, not an additional deployed product. `SduiFyneApplication` represents
the actual embedding process role; it is not a new binary created by this model.
Shared package boundaries and extraction targets are separate from current process
deployment. [Ecosystem coverage](../README.md) records the combined entrypoints.

## Public boundary and scenarios

The scenario summarizes a locally bound input commit. The command explicitly registers local input handlers and an example `ok` callback; symbolic SDL callbacks remain unbound. Native callbacks capture revisions, source candidates are adopted through `fyne.Do`, and invalid candidates leave the last valid UI visible.

`CommitNativeInputAccepted` and `CommitNativeInputRejectedScenario` describe the successful and
rejected logical call paths. The success result projection includes diagnostics; the rejection message has a
separate diagnostic-only contract and no generated/model/presentation payload. These named messages/channels
are analysis projections of Go calls, not shipped RPC names or wire contracts.
The closed contracts close only this deliberately bounded projection. They do
not claim all implementation fields or every interaction have been modeled.
Modes name operational contexts and do not implement a state machine.

## Limits and unresolved packaging

The native host is not an SVG-only viewer: it combines shared layout/background rendering with Fyne controls. It is not dependent on XFMD. Desktop execution needs display/OpenGL/X11/C tooling on Linux. This model authoring work does not launch a GUI or establish production Ponsse readiness.

Dedicated binary naming, installation and independently versioned library releases
remain extraction decisions. SDPTool can orchestrate public CLI or Go library
entrypoints; this model does not add a dependency or claim all integrations exist.
