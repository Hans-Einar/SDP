## Findings

### Medium

#### M-001 — The singleton CurrentAssignment contract cannot represent concurrent Issue Masters

**Location:** `SDP-usage-analysis/ProposedSDPWorkflow.md`, section
`CurrentAssignment recommendation`, lines 318-352; corroborating migration
language in `SDP-usage-analysis/MigrationImpact.md`, Phase 3, lines 64-71.

The recommendation keeps exactly one mutable
`Steering/CurrentAssignment.yaml`, and migration says to create “one prospective
current assignment.” It never defines whether the file is default-branch state,
worktree/branch-local state, a generated projection, or the only permitted active
assignment. It also defines no merge/conflict semantics or collection form for
two concurrently authorized Issues.

This is not hypothetical. `SDP-usage-analysis/repositories/TerrainAnalyzer.md`,
lines 106-113, records that Issue #12 authorized child Issues #14 and #15 from a
common base while the singleton still described the completed parent. Live
cross-check on 2026-08-21 found both draft PR #22 at
`4d9c090d6a10628a8a9759aa8ccad96d0876dd68` and draft PR #23 at
`0c0e6caec0f8fd3e50919970bafbcaacd362764c` open concurrently; both branch trees
still carry the same stale Issue #12 `CurrentAssignment.yaml`. A canonical
singleton would make valid parallel Issue Masters overwrite one another, merge
conflicting pointers, or disappear from the default-tree view.

Resolve the cardinality before schema work: define per-Issue assignment records
or an explicit branch-local record plus a generated multi-assignment index, and
specify default-branch, concurrency, merge, clear/advance and stale-detection
semantics.

#### M-002 — Real workflow pilots occur only after Analyzer and write-capable migration implementation

**Location:** `SDP-usage-analysis/FollowUpIssues.md`, follow-ups 2-8, lines
22-104, especially the dependencies at lines 66, 77, 87 and 104.

The ordering freezes schemas, updates canonical instructions/skills, implements
multi-generation Analyzer support, implements gh-sdp status/planning, and then
implements write-capable install/update/migrate apply before the first real
repository pilot. Yet `SDP-usage-analysis/CrossRepositoryPatterns.md`, lines
162-172, correctly says only two default trees exercise Feature ownership, two
exercise Refactor ownership, none exercises a first-class Fix, and only three
show accepted Issue-authoritative delivery. The proposed semantics are therefore
owner-directed and evidence-informed, not already proven as a complete contract.

This order can lock incorrect cardinality, status, profile and migration
assumptions into both downstream consumers before a real repository exercises
the method. Split the pilot gate: run non-destructive/manual workflow and schema
pilots after the semantic/schema/documentation work, use their evidence before
freezing Analyzer and gh-sdp contracts, and retain later apply/migration pilots
after the write path exists.

**Locations:** `SDP-usage-analysis/CrossRepositoryPatterns.md`, lines 162-166;
`SDP-usage-analysis/repositories/SDP-Analyzer.md`, lines 461-466.

The final skill document correctly labels separation as RECOMMENDATION. Split
the mixed claims so owner constraints are not expanded by the synthesis.
