## Material findings

1. **P1 — setup accepts transient executables and can report durable registration for a disappearing engine.** `SDPTool/runtime_setup.go:39-50` accepts every existing regular executable returned by os.Executable; `:66` immediately symlinks that path as the public runtime. There is no test for temporary/go-build/cache sources or an explicit stable supported installation boundary. Consequently `go run ... setup` or an engine copied under a disposable `/tmp` directory succeeds, and removal of that directory breaks all XFMD browsing despite a successful setup receipt. Current `runtime_test.go:15-25` actually registers the temporary Go test executable, reinforcing this unsupported behavior. This violates the implementation contract's explicit requirement that transient/deleted/unsupported sources fail clearly and undermines the single update owner. Define and enforce supported stable-source validation without hardcoding gh directory layout; reject transient sources before filesystem registration. Retain explicit developer overrides separately. Test the real process from transient and deleted locations, plus the actual gh-installed path.

2. **P1 — XFMD does not validate the selected shared-runtime capability contract.** `src/application/sdp/SdpToolJob.cpp:151-160` selects the public path, while `SdpProtocol.cpp:49-55` checks only the unchanged sdptool/0.2/actions schemas. No XFMD source examines the new `runtime.setup/1`, `sdui.source/1` or nativePrototypeBundled advertisement, and no version/capability handshake exists. An older engine with the same protocol schema therefore remains accepted for navigation and only later fails on the new SDUI commands with an ordinary unknown-operation error; incompatible registration is not reliably diagnosed at the intended boundary. Contract: XFMD validates protocol/capabilities and gives actionable missing/incompatible setup guidance. Probe the relevant advertised capability/action contract locally and fail affected workflows with the setup/update instruction; preserve intentional compatibility where an unrelated feature does not require SDUI. Include a schema-compatible old-engine fixture and an engine without bundled native support.

3. **P2 — canonical public contract is not reconciled with the new commands and registration behavior.** `SDPTool/Contract.md` has no setup command/public-path/conflict/migration section and no `sdui preview|check|run` host dispatch description; it still contains the previous package artifact description at line262. The new behavior is specified only in the Activity implementation contract and source. SDP document workflow requires durable behavior explanations in the canonical contract, not only work records. Update the maintained public contract/installation instructions, including Linux-amd64 qualification boundary, offline helper extraction and explicit setup conflicts, before closeout.
