### High

#### H-001 — Reservation identity is not required to exist in the durable inventory

**Locations:** `SDP-vnext-pilot/WorkDomains.md`, lines 117-136 and 164-173;
`SDP-vnext-pilot/ConcurrentAssignments.md`, lines 164-175;
`SDP-vnext-pilot/validate_pilot.py`, especially lines 2119-2152 and
2761-2784; and
`SDP-vnext-pilot/fixtures/positive/unreferenced-reservation-set.json`, lines
7-21.

The authored contract says `issuedIds` is the structured no-reuse inventory,
that a newly created reservation uses the prospective member's immutable
`allocationIssue`, and that preparatory rows resolve their ID/inventory
authority. The implementation instead does this in both the reusable
reservation validator and bound assignment validator:

```text
allocated_by = issued_by.get(key)
if allocated_by is not None and allocated_by != issue:
    ISSUED_ID_RECLAIM
```

An absent inventory member therefore receives no diagnostic. The positive
preparatory fixture itself adds inventory members for `FEAT-090` and
`FEAT-091`, but not for the authorized/reserved `SLC-090` and `SLC-091`, and is
treated as valid. This is not only a missing-format check:

- replacing both `SLC-090` references in the first preparatory row with
  valid-shaped, wholly un-inventoried `SLC-099` returned `[]`;
- adding wholly un-inventoried `FIX-099` to both sides of the accepted bound
  Issue 10 assignment/reservation and rebinding its digest returned `[]`; and
- adding the same absent `FIX-099` to a later preparatory Issue 90 row also
  returned `[]` for the combined document.

The last result defeats permanent no-reuse. Terminal bound epochs are correctly
excluded from current path/concurrency collisions, but an identity survives
that exclusion only through the durable inventory. When the reservation never
had an inventory member, the accepted historical claim disappears from the
current collision boundary and the same ID can be reserved again. A future
domain export/move would omit it for the same reason.

This is High because stable identity, collision prevention, concurrent Issue
Master allocation, and repository-split preservation are core Issue #7 pilot
decisions. A pilot can pass its pre-work reservation gate while lacking the
only durable fact that prevents another Master or successor repository from
reusing the ID.

**Required remediation:** require every qualified `reservedIds` member in a
bound or preparatory row to resolve to a durable current allocation member for
the same domain and require that member's immutable allocator to equal the row
Issue. Missing and `legacy-preserved` members must fail, not merely mismatched
members. Reconcile the preparatory lifecycle explicitly: if a Slice/Fix/Study
ID must be reserved before its full record can be materialized, add a typed
durable reserved-allocation state or another equally strong source/authority
surface rather than omitting it from the inventory. Preserve that allocation
after terminal epochs and through domain moves. Add exact negatives for an
absent bound ID, absent preparatory authorized ID, extra absent reserved ID,
and terminal-to-preparatory reuse, plus a valid fully inventoried preparatory
control.

### Medium

#### M-001 — Preparatory rows can claim accepted Slice candidates without acceptance

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, lines 166-175;
`SDP-vnext-pilot/ConcurrentAssignments.md`, lines 164-175; and
`SDP-vnext-pilot/validate_pilot.py`, especially lines 2075-2154 and
2413-2472.

The cardinality contract says an authorized entry stores
`acceptedCandidate: null` until acceptance and only then stores the immutable,
qualified Slice candidate. An unbound typed reservation object is defined as a
current preparatory epoch. Its row receives shape, ID, path, graph, order,
convergence and collision checks, but no check relates a non-null
`acceptedCandidate` to a bound accepted assignment or evidence-qualified Slice.

A fresh mutation of the valid `unreferenced-reservation-set.json` control set
the first preparatory `SLC-090.acceptedCandidate` to forty lowercase `a`
characters and changed nothing else. Full `validate_document()` returned `[]`.
There is no represented `SLC-090` record, accepted evidence, assignment, review,
verification, or Steering disposition.

This is Medium because the unbound row is not yet the repository's accepted
assignment, but it can serialize and hash a false immutable acceptance claim
inside the artifact that Masters are instructed to trust before activation.

**Required remediation:** under the current rule that every unbound typed set
is preparatory, require every authorized entry's `acceptedCandidate` to be
`null`. If a future use case needs an unbound historical set, give that object
an explicit state and require the same exact assignment/Slice evidence binding
as a terminal bound epoch. Add a dedicated negative fixture and retain the
legitimate null-candidate preparatory controls.
