### High

#### H-001 — Durable allocation does not preserve its one reservation epoch or immutable planned source

**Locations:** `SDP-vnext-pilot/WorkDomains.md`, lines 117-150;
`SDP-vnext-pilot/ConcurrentAssignments.md`, lines 173-188 and 193-212; and
`SDP-vnext-pilot/validate_pilot.py`, especially lines 533-560, 2038-2041,
2160-2176, 2516-2551, and 2841-2864.

The tenth candidate correctly requires every reservation claim to resolve to a
`reserved` or `prospective` inventory member and rejects claims allocated by a
different Issue. The member itself, however, contains only `id`, `status`,
`allocationIssue`, and `source`. It does not identify the one immutable
reservation-set epoch, candidate, or allocation event that first claimed the
identity. Cross-epoch no-reuse is computed only from reservation objects still
present in the current validation document.

This leaves two related history attacks green:

1. A preparatory/cancelled reservation may be removed while its `reserved`
   inventory member remains. A later preparatory set under the same Issue can
   claim the same ID because allocator equality succeeds and the missing old
   set contributes no epoch to `all_id_claims`. A self-contained reconstruction
   using the simple example—no old assignment/set, the still-reserved
   `SLC-001`, and a new preparatory set for the same Issue/ID—returned `[]`.
   The current bytes cannot distinguish this from the first allocation even
   though the contract calls reservation a one-time claim, not a renewable
   lease.
2. Starting from the valid reserved-before-materialization control, promoting
   `SLC-090` to `prospective` while changing both the inventory `source` and
   materialized record `source` from `Slices/SLC-090.json` to
   `Slices/Renamed-SLC-090.json` returned `[]`. The static source binding is
   internally consistent, but no generic inventory history proves the stated
   rule that promotion changes only `status`.

The adjacent collision rule is working: making distinct reserved IDs claim
the same normalized planned source emitted `DUPLICATE_INVENTORY_SOURCE`.
Therefore the gap is not normalization; it is missing durable allocation
provenance and transition history.

This is High because permanent identity no-reuse and recovery after cancellation
are core Issue #7 concurrency guarantees. A deleted cancelled set or rewritten
promotion can pass and later be copied into a successor repository as if it
were the original allocation.

**Required remediation:** define the pilot cancellation/allocation lifecycle
explicitly. Bind every current allocation member to one immutable allocation
epoch/candidate (or an append-only allocation ledger with equivalent evidence),
preserve that binding after cancellation/rejection/supersession and across
moves, and have the repository driver compare inventory transitions. A
cancelled unused ID may be intentionally burned, but it MUST NOT become a fresh
claim. Promotion MUST prove unchanged UID, ID, allocator, allocation epoch, and
planned source while changing only status and materializing the record. Add
exact controls for same-allocator replay after cancellation/history omission
and planned-source rewrite during promotion.

#### H-002 — Reserved inventory becomes impossible to materialize after its domain moves

**Locations:** `SDP-vnext-pilot/WorkDomains.md`, lines 125-155, 181-190,
207-219, and 284-296; `SDP-vnext-pilot/HSX-Pilot-Handoff.md`, lines 123-133 and
163-174; and `SDP-vnext-pilot/validate_pilot.py`, especially lines 2044-2089,
2160-2176, 2645-2691, and 2841-2864.

The move contract requires the successor to import byte-equivalent reserved
inventory, including the immutable `allocationIssue`. The repository-coherence
contract separately requires every reservation row, assignment Issue, and PR
to belong to the repository that actively hosts the primary domain. For a
reserved Slice allocated before the move, these rules cannot both be
satisfied:

- preserve the old-repository `allocationIssue` and use a new destination
  Issue: validation emits `AUTHORIZED_SLICE_ALLOCATION_MISMATCH` and
  `ISSUED_ID_RECLAIM`;
- keep executing under the old allocator Issue so equality holds: validation
  emits `REPOSITORY_AUTHORITY_MISMATCH` because the active host is now the
  destination repository.

Fresh reconstruction added the same reserved `DBG-SLC-001` member to the old
tombstone and active successor. Exact inventory preservation passed, and a
source rewrite correctly emitted `MOVE_ID_INVENTORY_REWRITE`. Promoting the
preserved member and authorizing an active Slice from the destination produced
the conflict above. Thus inventory copying is validated, but legitimate
materialization after the move is impossible.

This is High because Issue #7 explicitly requires reserved inventory and
identity continuity when a domain later moves. The first HSX pilot is required
to produce a no-rewrite move plan; it cannot do that truthfully for an in-flight
reserved Slice under the present rules.

**Required remediation:** choose and encode one explicit move disposition for
every reserved member before the move gate. Either (a) permit continued
materialization through a provenance-preserving transfer/execution authority
that keeps the original allocator immutable while authorizing a canonical
destination Issue, or (b) require every pre-move reservation to materialize or
be permanently cancelled/burned before host transfer. In both cases preserve
the ID/source/allocation evidence and make the outcome deterministic. Add a
positive reserved-inventory move plus destination materialization control and
negatives for unauthorized transfer and allocator/source rewrite.

### Medium

#### M-001 — Terminal cancellation can leave an active Slice outside the current collision boundary

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, lines 130-133, 148-175,
and 274-279; `SDP-vnext-pilot/ConcurrentAssignments.md`, lines 193-212; and
`SDP-vnext-pilot/validate_pilot.py`, especially lines 2455-2471, 2522-2531,
2739-2794, and 2874-2917.

Pilot v0 classifies an epoch as historical when all bound assignments are
`accepted`, `rejected`, `cancelled`, or `superseded`, so its paths cease to
participate in current collision checks. Only `accepted` assignments are
required to clear `activeSlices`, and active-Slice state/projection checks run
only when the assignment itself is `active`.

A fresh mutation changed all three scoped-example assignments to `cancelled`
without changing their `activeSlices` or the represented
`DBG-SLC-001`/`SHARED-SLC-001` records, which remained `declaredState: active`.
Full `validate_document()` returned `[]`. The repository can therefore declare
active execution while the concurrency model has already released its paths
for reuse.

This is Medium because cancellation is a valid Steering outcome and path
release may be desirable, but the present state can mislead a recovering Master
and permit a later writer while the durable Slice still says active.

**Required remediation:** define terminal closeout for `cancelled`, `rejected`,
and `superseded`. At minimum require `activeSlices: []`, forbid represented
Slices for that assignment from remaining `active`, preserve the exact terminal
assignment/reservation, and state when paths are released versus IDs remain
burned. Add one valid cancellation closeout and invalid terminal-with-active-
Slice fixtures for each terminal non-accepted state.
