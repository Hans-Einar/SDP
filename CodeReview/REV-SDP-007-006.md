### High

#### H-001 — Preserved assignments from different execution episodes are misclassified as concurrent

**Locations:** `SDP-vnext-pilot/ConcurrentAssignments.md`, especially lines
33-47 and 145-168; `SDP-vnext-pilot/IssueContract.md`, assignment mirror;
`SDP-vnext-pilot/WorkflowContract.md`, lines 143-170 and 377-385; and
`SDP-vnext-pilot/validate_pilot.py`, lines 2120-2139 and 2463-2479.

The contract says one reservation set contains every **concurrent** assignment,
while accepted per-Issue assignment records are preserved as durable terms.
The validator instead applies one common base, one reservation-set identity,
one convergence contract, all path collisions, and shared symmetry across the
entire `assignments` collection regardless of assignment state or reservation
set.

A fresh mutation started from the valid delivered Feature with two accepted
Issues/two Slices. It retained both accepted assignments but gave Issue 10 and
Issue 12 their own digest-bound one-row historical reservation sets, own merge
orders, and exact bases (`2222...` and later `4444...`). Neither set contained
a current dependency or conflict; both were independently complete, both
assignments/Slices remained accepted at their original candidates, and paths
were disjoint. Validation returned only:

```text
CONVERGENCE_CONTRACT_MISMATCH
STALE_COMMON_BASE
```

Changing the later sequential episode to reuse `src/export/**`—a normal reason
to extend the same Feature—also returned `PATH_COLLISION`, even though the two
accepted assignments were in different historical sets and never concurrent.

The supplied `feature-two-issues-two-slices` control avoids the defect by
placing both Issues on the original common base and in one synthetic
reservation set. It therefore proves only a pre-reserved concurrent wave, not
the required “one work owner has several Issue assignments over time” case.
A real HSX repository that preserves closed assignment records would
eventually fail as soon as a later Issue starts from the advanced integration
head or legitimately touches an earlier area.

**Required remediation:** define the current/concurrent reservation-set
projection explicitly. Group base, digest, dependency/conflict, merge,
convergence, path-collision, and shared-symmetry checks by the applicable
reservation set/current activation epoch. Preserve accepted historical
assignments from other sets as terminal graph evidence without treating them
as current writers. Add positives for two accepted sequential Issues with
distinct sets/bases and for later path reuse, while retaining collision
negatives inside one concurrently active set.

#### H-002 — Revision history permits primary-work replacement and accepted-Slice erasure

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, lines 147-170 and
280-291; `SDP-vnext-pilot/ConcurrentAssignments.md`, lines 65-84;
`SDP-vnext-pilot/fixtures/positive/accepted-issue-reopen-revision.json`, lines
5-23; and `SDP-vnext-pilot/validate_pilot.py`, lines 2482-2617 and
2689-2745.

The committed positive called “accepted Issue revision adds new Slice and
preserves earlier candidate” does not have that history. Its source is the
Issue #7 dogfood chain. Fresh reconstruction of its immediate predecessor
showed:

```text
revision 4 workRef: STU-007 (study)
revision 4 activeSlices: []
revision 4 authorizedSlices: absent
revision 5 workRef: FEAT-007 (feature)
revision 5 authorizedSlices: SLC-007@1111..., SLC-008@2222...
```

The fixture replaces the Study with a different primary work owner and creates
both Slices only in revision 5. It therefore cannot prove that `SLC-007` was
accepted before reopen. More importantly, deleting `SLC-007` from the current
Feature, records, inventory, assignment, reservation row, and reserved IDs,
then rebinding the current reservation digest, still returned `[]` under the
repository driver. The remaining `SLC-008` passed and no historical comparison
noticed the purported earlier accepted Slice had disappeared.

History validation checks chain links and only the arbitrary JSON pointers a
snapshot elects to put in `recordedContext`; it does not require immutable
`workRef`, preserve prior accepted `authorizedSlices`, or compare the current
set with the historical assignment bytes. The repository driver also copies
the historical assignment's reservation digest string but does not load and
rehash that historical reservation file generically. The exact Issue #7
revision-1..5 chain is valid when independently rehashed; the defect is the
reusable contract and its claimed reopen proof.

This permits a revision to change what one bounded Issue was primarily about
and to remove accepted outcomes while retaining a structurally valid history
chain—the evidence rewrite the revision model exists to prevent.

**Required remediation:** keep canonical Issue and primary `workRef` immutable
across assignment revisions; require every accepted authorized-Slice identity
and candidate from the historical assignment to remain in later revisions;
and compare those fields from the actual historical assignment, not optional
snapshot pointers. Rehash each historical reservation file from its exact Git
candidate. Replace the positive with a real two-candidate sequence whose prior
revision actually contains accepted `SLC-007`, then add deletion, candidate
rewrite, work-owner replacement, and historical-reservation-tamper negatives.

### Medium

#### M-001 — `activeSlices` is not a complete projection of declared-active Slices

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, lines 147-170 and
363-391; `SDP-vnext-pilot/validate_pilot.py`, lines 1618-1689,
2289-2336, and 2404-2445.

Starting from the valid one-Issue/two-sequential-Slice positive, a fresh
mutation changed both `SLC-001` and `SLC-002` to `declaredState: active` with
null evidence, changed the assignment to active, cleared both authorized
candidates, and named only `SLC-002` in `activeSlices`. The reservation row was
changed identically and rebound. Validation returned `[]`.

The validator proves every active pointer resolves to an active authorized
Slice, but never proves the reverse: every Slice for that assignment declared
active must be the one pointer. A repository can therefore expose two
currently executing Slices while the compact coordination record and
reservation claim only one.

**Required remediation:** for an active implementation assignment, require the
set of its represented Slices with `declaredState: active` to equal
`activeSlices` exactly; retain the `0..1` cardinality and accepted historical
authorized Slices. Add an exact two-declared-active/one-pointer negative and a
valid one-active-plus-earlier-accepted control.

#### M-002 — Terminal Fix affected-work closure accepts an owner with no accepted outcome

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, lines 62-74 and
377-391; and `SDP-vnext-pilot/validate_pilot.py`, lines 1752-1839.

Starting from the accepted standalone-Fix positive, a fresh mutation left the
Fix delivered and its own zero-Slice assignment accepted, but changed the
affected Feature, its only Slice, and its only Issue assignment to active; the
Slice and assignment evidence became null and the Slice became the current
active Slice. The Fix assignment's execution dependency on that Issue was
removed from both bound projections. The Feature retained a syntactically
qualified aggregate evidence object. Validation returned `[]`.

The terminal Fix check accepts an affected owner in state `active` when its
owner-level evidence object is well shaped. It does not prove that the active
owner has any preserved accepted assignment/Slice. Thus a genuine Fix can be
declared delivered against behavior whose only represented implementation
outcome is still unaccepted.

**Required remediation:** when `affectedWork` names an active durable owner,
resolve its qualified evidence to at least one preserved accepted assignment
and accepted behavior Slice (or require the Fix to reference that accepted
surface directly). Keep the valid case where a Feature returned to active
after earlier accepted delivery. Add exact active-owner-with-and-without-
accepted-history controls for sliced and standalone Fixes.

#### M-003 — Top-level semantic edges bypass relation-specific kind semantics

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, lines 184-218; and
`SDP-vnext-pilot/validate_pilot.py`, lines 1499-1539 and 1541-1586.

Embedded Study and Fix fields define and validate semantic shapes such as
Study `owned_by` work owner, Study `independent_of` Study, Study `informs`
work/Study, and Fix `corrects` work owner. Top-level relations only require
both endpoints to be any stateful record. Fresh additions to the valid move
example all returned `[]` when a Feature authored each of these top-level
relations to another Feature:

```text
corrects
owned_by
independent_of
informs
```

These are not equivalent to the embedded meanings and contradict the
contract's statement that wrong-kind semantic edges are errors across the one
global set. Relation-specific DAG traversal is otherwise working, and the
non-DAG reciprocal `preserves` positive remains valid.

**Required remediation:** define one relation-type source/target-kind matrix
and enforce it for both embedded and top-level forms before duplicate/DAG
processing. Add top-level wrong-source and wrong-target negatives for
`corrects`, `owned_by`, `independent_of`, and `informs`, plus valid top-level
equivalents of the embedded edges.

#### M-004 — Duplicate JSON member names are silently accepted and hashed

**Locations:** `SDP-vnext-pilot/README.md`, strict JSON description;
`SDP-vnext-pilot/ConcurrentAssignments.md`, canonical JSON rules; and
`SDP-vnext-pilot/validate_pilot.py`, lines 178-180 and 2670-2713.

`load_json()` rejects the non-standard constants `NaN` and infinities, but uses
the standard loader without an `object_pairs_hook`. A probe of exact input

```json
{"experimental":true,"pilot":1,"pilot":2}
```

silently produced `{"experimental": true, "pilot": 2}` and a canonical
digest. Different conforming consumers may keep the first member, keep the
last, or reject the object. Applied to `issue`, `workRef`,
`integrationBase`, or a reservation row, that ambiguity defeats the portable
authority/digest contract even though every retained value is finite.

**Required remediation:** reject duplicate member names recursively during
all example/template/dogfood/history parsing and historical Git-blob parsing,
return a stable diagnostic, and add bound-reservation/assignment fixtures. Do
not compute a canonical digest from an ambiguously parsed source object.

### Low

#### L-001 — Invalid Unicode in a branch name crashes validation

**Locations:** `SDP-vnext-pilot/validate_pilot.py`, lines 183-204 and
324-337.

Replacing an assignment delivery branch with the JSON-escaped value
`codex/a\ud800b` caused `validate_document()` to raise an uncaught
`UnicodeEncodeError` at `len(value.encode("utf-8"))`. The document-wide scalar
check had already identified the surrogate, but validation continued into
`valid_branch` before returning the diagnostic. The bound-path surrogate case
is correctly stable; this neighboring branch field is not.

**Recommended remediation:** reject invalid Unicode scalars before encoding a
branch value (or catch the encoding failure), return `INVALID_UNICODE_SCALAR`
plus the branch diagnostic, and add an exact fixture.

   resolved as Git objects or proven to include historical Slice candidates.
   A delivered Feature with aggregate candidate `0000...` returned `[]` in an
   isolated example. This is not raised separately because observed remote
   resolution and exact verification/review may supply that proof, but the
   first HSX pilot MUST record candidate existence and integration/inclusion
   rather than treating shape validation as evidence.

   non-finite and is rejected, while `9007199254740993` and underflowing
   `1e-400` are accepted/digested by Python (the latter becomes `0.0`). The
   current contract promises finite JSON, not I-JSON numeric range/exactness.
   Cross-language numeric limits should be decided before schema freeze.
3. The handoff's success section asks for two synthetic or real disjoint
   assignments, while its proposed downstream Issue and stop condition require
   one pilot assignment/Slice. Steering should make the second assignment a
   real separately authorized Issue or state that concurrency evidence is a
   later pilot; a synthetic canonical-looking URL must not be mistaken for
   Issue authority.
4. Fresh local reruns were Windows-only. Exact-head Actions run `32514457819`
   supplies the unchanged Ubuntu Toolkit contracts/unit tests and Windows
   installer job, but the workflow does not run the provisional pilot
   validator on Linux.
5. GitHub exposes repository activity primarily through `Hans-Einar`; fresh
   task context provides process separation, not independently signed external
   actor provenance. Live GitHub/ref/check observations may change after this
   record.
6. This review did not migrate HSX, run two live writing Masters, perform a
   real repository split, run HSX product/platform tests, or publish anything.
   Those remain downstream pilot work after the contract itself has no
   unresolved Blocking/High/Medium finding.
