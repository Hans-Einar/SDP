### High

#### H-001 — Multi-Issue and sequential-Slice cardinality contradict the durable lifecycle

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, especially lines 143-169,
151, 259-264, and 338-354; the Steering-accepted
`SDP-usage-analysis/ProposedSDPWorkflow.md`, especially lines 109-114 and 216;
`SDP-vnext-pilot/validate_pilot.py`, especially lines 1531-1545, 2044-2046,
and 2133-2164.

Issue #7 and the accepted synthesis require one durable Feature to support one
or more Issue assignments over time, one Issue to contain several sequential
Slices, and accepted work to extend through a new Issue/Slice without rewriting
earlier identity or evidence. The pilot cardinality table likewise says a work
owner has `0..N` Issues and an Issue has `0..N` Slices.

Two current rules make those ordinary cases fail:

1. The prose at lines 168-170 and validator at lines 2044-2046 require every
   assignment Issue to equal the primary work record's prospective inventory
   `authorityIssue`. That inventory value is the allocation authority for the
   stable Feature ID. A legitimate later Issue assigning more work to the same
   Feature therefore cannot pass: changing the inventory authority to the new
   Issue only makes the original assignment fail instead.
2. Every represented Slice must be listed by the one current assignment for its
   Issue, while an accepted assignment requires every listed Slice evidence
   candidate to equal the assignment candidate. Two sequential accepted Slices
   at immutable candidates A and B therefore fail at B. Removing the earlier
   Slice from current `activeSlices` makes it orphaned; changing its evidence
   candidate to B rewrites the accepted evidence that the reopen/extension rule
   says remains immutable. Assignment-history snapshots are not considered by
   the Slice graph, so revision/refreeze does not supply another valid route.

Fresh fully shaped probes reproduced both contradictions:

- a second Issue 12 allocated a new `SLC-002`, added itself to the durable
  `FEAT-001` authorities, used disjoint paths, a complete digest-bound two-row
  reservation set, and a valid merge/convergence order. The only diagnostic
  was `PRIMARY_WORK_AUTHORITY_MISMATCH` against the Feature's original Issue 10
  allocation authority;
- one Issue 10 accepted `SLC-001` at candidate `1010...` and later accepted
  `SLC-002` at candidate `1212...`, with the assignment accepted at the final
  candidate and a complete rebound reservation. The only diagnostic was
  `ASSIGNMENT_CANDIDATE_MISMATCH` for the earlier immutable Slice.

This is not an optional future schema choice. It prevents the exact Feature ->
several Issues, Issue -> sequential Slices, and accepted-Issue reopen/extension
semantics that Issue #7 makes part of the pilot work contract.

**Required remediation:** distinguish stable-ID allocation authority from later
execution authorities. A later assignment may reference an already-issued
Feature/Refactor/Fix when its Issue appears exactly once in that work owner's
assignment authorities; it is not reclaiming or reserving the owner ID.
Continue enforcing allocation authority for newly reserved IDs. Represent the
complete authorized Slice set separately from the currently active Slice, or
otherwise preserve old Slice-to-assignment resolution across revisions. An
accepted multi-Slice assignment must aggregate independently qualified Slice
candidates without replacing earlier evidence; when ancestry/inclusion is
required, validate that relation explicitly rather than requiring candidate
string equality. Add positive fixtures for a second-Issue Feature extension,
two sequential Slices in one Issue, and accepted-Issue reopen with a new Slice,
plus exact negative adjacency controls.

fixtures for active/unaccepted standalone-Fix assignment, missing owner

#### M-001 — Multi-hop semantic dependency cycles pass the global graph

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, especially lines 172-199;
`SDP-vnext-pilot/validate_pilot.py`, especially lines 1363-1490; and
`SDP-vnext-pilot/examples/domain-move.json`, lines 172-200.

The fifth candidate correctly normalizes embedded and top-level edges into one
set, rejects duplicates and direct self-edges, and treats `depends_on` as a
gating relation. The global graph does not traverse those edges for cycles.

A fresh mutation retained the valid proposed `HOST-FEAT-001 -> DBG-FEAT-001`

`DBG-FEAT-001 -> HOST-FEAT-001` dependency. Both records remained proposed and

An execution reservation DAG is separately acyclic, but that does not repair a

**Required remediation:** validate `depends_on` as an acyclic global semantic

`refines`, or `requires_revision`) also require acyclicity, without treating
legitimately symmetric/non-gating relations as a DAG. Add two- and three-hop
cross-scope cycle fixtures and a valid diamond dependency control.

#### M-002 — Non-finite scalars produce a digest for bytes that are not canonical JSON

**Locations:** `SDP-vnext-pilot/ConcurrentAssignments.md`, lines 37-48;
`SDP-vnext-pilot/README.md`, lines 43-52;
`SDP-vnext-pilot/validate_pilot.py`, especially lines 170-191, 1686-1750, and
2735-2746.

Pilot v0 defines the reservation digest over canonical JSON bytes so different
assignments and future tools can reproduce one content identity. Python's JSON
loader/encoder accepts non-standard `NaN`/infinity values by default, and
`canonical_digest()` rejects only surrogate code points. Outer objects are
intentionally extension-tolerant, so a non-finite scalar can reach the digest
without any field-level validator seeing it.

A fresh probe added `pilotExtensionNumber: NaN` to the bound reservation set,
recomputed the assignment digest, and ran full validation. The validator
produced digest
`sha256:e6029ab33de57ec0648258bef91cc0ef039e8986c945b3c0ee2794347aa55afc`
and returned `[]`. The encoded bytes contain bare `NaN`, which JSON does not
define and strict cross-language parsers reject. By contrast, a Boolean in the
digest field itself correctly returns `INVALID_RESERVATION_DIGEST`, and the
bound lone-surrogate fixture correctly returns stable scalar/path diagnostics.

**Required remediation:** recursively reject non-finite floats before hashing
or parsing a pilot document, use strict JSON loading (`parse_constant` failure)
and encoding (`allow_nan=False`), and return a stable diagnostic such as
`INVALID_JSON_SCALAR`. Add bound-reservation fixtures for `NaN`, positive and
negative infinity, including occurrence in extension objects, plus an ordinary
finite numeric extension control.
