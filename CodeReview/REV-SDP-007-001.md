### High

#### H-001 — The validated record graph can violate the core Slice and Issue cardinalities

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, lines 78-93 and 132-145;
`SDP-vnext-pilot/examples/scoped-monorepo.json`, lines 197-223 and 239-381;
`SDP-vnext-pilot/examples/domain-move.json`, lines 90-122; and
`SDP-vnext-pilot/validate_pilot.py`, lines 403-432 and 517-589.

The contract requires every Slice to have one primary work owner and exactly
one authorizing assignment, with explicit owned/shared paths. The scoped
positive example nevertheless declares `SHARED-SLC-001` for Issue 203 while
the document contains assignments only for Issues 201 and 202. The repository-
move positive example declares `DBG-FEAT-001` delivered with zero Issue
authorities and references `DBG-SLC-001`, but contains no Slice record.

The validator makes both documents pass. When a work owner references a missing
Slice, lines 428-430 silently continue. Assignment validation checks only the
Slices listed by an assignment; it never proves that every Slice's
`assignmentIssue` resolves exactly once. It also never normalizes or resolves a
Slice's `decisionRefs`, `ownedPaths`, or `sharedTouchpoints`, nor checks that
those paths are authorized by its assignment.

Adversarial mutations confirmed that validation returns no diagnostics when a
Slice uses `../outside`, names an undeclared shared path, or contains a bare
decision reference. It also returns no diagnostics when delivered work has no
Issue authority. A first HSX pilot could therefore pass while its Worker
contract writes outside the common-base reservation or while a Slice has no
Issue Master.

**Required remediation:** validate the graph from both directions. Every typed
Slice must resolve to exactly one assignment and one Feature/Refactor/Fix owner;
the assignment, Slice, owner `slices`, and Issue authority must agree. Normalize
and validate Slice paths/references, prove its private paths are contained by
the assignment reservation, and prove its shared paths match declared shared
touchpoints. Enforce state-dependent Issue/Slice cardinalities. Repair both
positive examples and add exact negative fixtures for orphaned assignment,
missing referenced Slice, unreserved/invalid Slice path, and unqualified Slice
decision reference.

#### H-002 — The concurrent-assignment PASS is not tied to the shared reservation contract

**Locations:** `SDP-vnext-pilot/ConcurrentAssignments.md`, lines 33-61 and
76-87; `SDP-vnext-pilot/Examples.md`, lines 32-39;
`SDP-vnext-pilot/examples/scoped-monorepo.json`, lines 239-381; and
`SDP-vnext-pilot/validate_pilot.py`, lines 472-501, 514-516, and 761-845.

The contract requires one published, digest-bound reservation set containing
every concurrent Issue, ID, path, dependency/conflict edge, merge order, and
convergence gate. The scoped concurrency example supplies only the same
placeholder digest string in each assignment; there is no reservation-set
document to hash or compare. Generic validation checks tuple equality and
digest syntax, not the referenced bytes or assignment-to-reservation field
equivalence. The stronger checks at lines 761-845 are hard-coded to the
single-Issue SDP dogfood filenames and first reservation row, so they cannot
validate the reusable concurrent example or a future HSX pilot.

Adversarial mutations produced no diagnostics for each of these invalid
states:

- two complete assignments with the same Issue URL, duplicate ID reservation,
  and overlapping private path;
- a directed dependency cycle between Issues 201 and 202;
- a merge order that omits Issue 202; and
- an arbitrary same-shaped reservation digest unrelated to any document.

Duplicate Issue authority is particularly dangerous: the `issue_map`
comprehension overwrites one row, while ID/path collision checks deliberately
ignore collisions attributed to the same authority string.

**Required remediation:** define a reusable pilot reservation-set template and
generic resolver. For every assignment set, resolve the exact reservation
document, recompute its canonical digest, and compare the complete Issue/work/
ID/path/shared/dependency/conflict/order/convergence content. Require unique
Issue authorities, valid local edge targets, an acyclic dependency graph,
symmetric conflicts, merge-order coverage without duplicates, order consistent
with dependencies, and an explicit convergence terminal. Add adversarial
fixtures for each case and make the scoped positive example use a real
reservation document rather than a placeholder digest.

### Medium

#### M-001 — Most record shapes cannot carry evidence-qualified accepted state

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, lines 117-123, 144-145,
and 181-191; `SDP-vnext-pilot/templates/refactor.template.json`, lines 1-22;
`SDP-vnext-pilot/templates/fix.template.json`, lines 1-19;

`SDP-vnext-pilot/examples/scoped-monorepo.json`, lines 61-81; and
`SDP-vnext-pilot/validate_pilot.py`, lines 44-80.

The contract correctly says acceptance requires an exact candidate,
verification, current independent review, and required Steering disposition.
Only the Feature required-field set has `acceptedEvidence`. Refactor, Fix,
Study, Slice, and assignment shapes have criteria or declared state but no
consistent accepted-evidence/disposition binding. The positive HSX-like Study
then declares `HSX-STU-001` `accepted` and makes the Debugger Feature depend on
it using only findings and a prose convergence gate.

This conflates declared lifecycle text with the separate accepted projection
that the contract says must remain evidence-qualified. The validator likewise
accepts `delivered`/`accepted` records with null or absent evidence.

**Required remediation:** choose one explicit pilot representation—common
`acceptedEvidence` fields or qualified links to separate evidence/disposition
records—for every stateful work kind and assignment. It must identify the exact
candidate, qualifying verification, current review, and Steering disposition
where required. Validate lifecycle/state transitions against those fields and
add negative fixtures for unsupported `accepted`, `delivered`, and `released`
claims. Update the accepted Study example to carry real synthetic evidence.

#### M-002 — The identity inventory can duplicate, accept malformed, or reissue IDs and still pass

**Locations:** `SDP-vnext-pilot/WorkDomains.md`, lines 19-23, 90-123, and
137-147; `SDP-vnext-pilot/templates/work-domain-registry.template.json`, lines
1-20; `SDP-vnext-pilot/HSX-Pilot-Handoff.md`, lines 94-118; and
`SDP-vnext-pilot/validate_pilot.py`, lines 167-248 and 567-581.

The contract says a normalized ID is issued or reserved only once across the
domain's history and says legacy-preserved IDs carry source evidence. The
registry shape stores only bare `issuedIds` strings. Registry validation does
not check normalized duplicates, ID grammar/domain prefix for prospective IDs,
or legacy status/source evidence. Reservation validation compares only one
assignment against other assignments in the same document; it does not prevent
reclaiming an already-issued historical ID.

Adversarial mutations confirmed no diagnostics for duplicate `FEAT-001`, a
malformed `not-an-id` inventory member, or an assignment newly reserving the
already-issued `FEAT-001`. Set conversion during move comparison also erases
duplicate evidence. This is material to HSX because its handoff depends on a
complete, exact inventory of legacy `RF`, `DA`, and `ST` spellings before
allocating `SHARED-REF-001`/`SHARED-SLC-001` and before any later repository
split.

**Required remediation:** give inventory members enough structure to
distinguish prospective IDs from legacy-preserved IDs and cite exact source
evidence. Enforce normalized uniqueness, prospective key/type grammar,
no-reuse across issued and reserved sets, and inventory preservation across a
move; permit historical HSX spellings only through the explicit legacy path.
Add negative fixtures for duplicate/malformed issued IDs and issued-versus-
reserved reuse, plus one positive legacy HSX-shaped inventory fixture.
