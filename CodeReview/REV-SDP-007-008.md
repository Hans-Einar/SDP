### High

#### H-001 — Existing but disconnected Git commits can fabricate assignment history

**Locations:** `SDP-vnext-pilot/ConcurrentAssignments.md`, especially lines
69-105; `SDP-vnext-pilot/IssueContract.md`, lines 125-149; and
`SDP-vnext-pilot/validate_pilot.py`, `load_historical_json()` at lines
2771-2808 and `validate_assignment_history()` at lines 2953-3220.

The eighth candidate now reconstructs exact assignment and reservation bytes,
strictly parses them, rehashes the reservation, validates its complete graph,
selects exactly one canonical Issue row, and compares that row structurally to
the historical assignment projection. Those are material repairs. The
repository driver nevertheless checks only:

```text
git cat-file -e <sourceCandidate>^{commit}
git show <sourceCandidate>:<assignment-or-reservation-path>
```

It never receives or derives the exact current subject candidate, never runs an
ancestry check, and never proves that revision candidates are ordered ancestors
of one another and of the current assignment candidate.

A fresh real-Git probe started from the valid
`accepted-issue-reopen-revision.json` control. In a temporary repository it
committed the exact valid revision-1 assignment and reservation at root commit
`6cce3ac48919a145f405cb05cce40d43b94dd839`, created unrelated root commit
`dcbd5cc8977e286805fa428b2472746233c1a98c` as the current subject, and proved
with `merge-base --is-ancestor` that the historical commit is **not** an
ancestor. The snapshot, immediate-predecessor link, digest, exact row and
assignment semantics were otherwise coherent. Full
`validate_document(..., repository_root=<temp>, materialize_repository=False)`
returned `[]`.

An attacker or mistaken Master can therefore manufacture a fully valid-looking
prior chain on an unrelated branch or disconnected commit, point the current
snapshots at it, and pass the repository driver. Exact bytes and digests prove
integrity of the cited objects, not that they are the actual earlier states of
the reviewed assignment. This defeats the durable reopen/refreeze history that
the Issue #7 pilot uses to prevent evidence replacement.

**Required remediation:** make the repository driver candidate-aware. Require
every historical `sourceCandidate` to be a reachable ancestor of the exact
reviewed/current assignment candidate, and require the snapshot sequence to be
ancestry-ordered under an explicit merge-history policy. Reject disconnected,
descendant, self/current, and out-of-order candidates. Add a valid ordered Git
chain control plus exact disconnected-root, descendant, and reordered-chain
negatives. Keep the current exact assignment/reservation byte, row, digest and
append-only comparisons.

#### H-002 — Preparatory reservation sets bypass the repository collision boundary

**Locations:** `SDP-vnext-pilot/README.md`, lines 73-80;
`SDP-vnext-pilot/ConcurrentAssignments.md`, lines 137-155;
`SDP-vnext-pilot/WorkDomains.md`, lines 107-139 and 201-249; and
`SDP-vnext-pilot/validate_pilot.py`,
`validate_reservation_set_semantics()` at lines 1986-2266,
`validate_reservation_sets()` at lines 2269-2371, and assignment-only
inventory/collision checks in `validate_assignments()` at lines 2374-2768.

The candidate correctly applies complete **internal** base, row, graph,
merge-order, convergence, path, and shared-touchpoint checks to every typed set,
including an unbound one. Document-level authority, identity inventory, and
current-epoch collision checks still run only through bound assignment records.
The unbound set's rows are consequently not checked against the registry host,
known domain UIDs, already issued/reserved IDs, or active assignment paths.

Fresh mutations of the valid `unreferenced-reservation-set.json` control each
returned `[]` when the preparatory set:

- used an otherwise valid but undeclared `domainUid` for its primary work;
- used an otherwise valid but undeclared `domainUid` for its reserved Slice;
- moved its Issue authority to `https://github.com/example/other/issues/90`
  while retaining the `tiny-app` work domain;
- reserved existing `SLC-001`, already prospectively allocated by Issue 10;
  or
- in the active scoped example, used a new Issue 299 row to reserve the current
  `DBG-SLC-001` and overlap the active `src/debugger/inspection/**` private
  path.

The unchanged disjoint preparatory positive still returned `[]`, and a valid
terminal-plus-current same-ID/different-digest epoch control also passed. The
problem is therefore not that unbound preparation must be forbidden. It is
that the pre-binding artifact can claim validation while violating the exact
repository-wide no-reuse/collision checks that reservation is supposed to run
before Masters start.

The adjacent current binding also permits an authorized `SLC-001` to disappear
from both assignment and reservation `reservedIds` while inventory, Slice and
authorization records remain; after digest rebinding full validation returned
`[]`. Structured inventory prevents a second represented record from claiming
that ID, but the reservation no longer proves that the current assignment
actually reserved its authorized new identity.

**Required remediation:** validate every preparatory row against the hosting
registry and current repository reservation projection before it can be called
valid. At minimum require known domain UIDs, repository-coherent Issue
authority, issued-ID allocation/no-reclaim consistency, authorized-new-ID to
reserved-ID coverage, and collision checks against the one current bound epoch.
If several alternative drafts must coexist, add an explicit non-authoritative
draft state rather than treating all typed objects as activation-ready. Retain
the valid disjoint unbound control and add exact unknown-domain,
cross-repository, issued-ID-reclaim, active-ID/path-collision, and missing
authorized-reservation fixtures.

### Medium

#### M-001 — Early compatibility normalization is not limited to the early revisions

**Locations:** `SDP-vnext-pilot/ConcurrentAssignments.md`, lines 97-105;
`SDP-vnext-pilot/WorkflowContract.md`, lines 285-294; and
`SDP-vnext-pilot/validate_pilot.py`,
`normalize_historical_reservation()` at lines 2848-2950 and its unconditional
use in `validate_assignment_history()`.

The contract says compatibility recognizes two exact early Issue #7 forms:
revision 1's typed set-level edge/string-ID representation and revisions 2-4's
absence of `authorizedSlices`. Unknown or partially matching later shapes are
supposed to fail closed. The normalizer receives only reservation and
assignment objects; it never receives the revision/candidate compatibility
boundary. It therefore selects compatibility solely from the row's member set.

Fresh probes established:

- removing `authorizedSlices` from the exact revision-5 reservation row causes
  the normalizer to add an empty array and makes the normalized row exactly
  equal the revision-5 assignment projection;
- the revision-1 set-level legacy shape is accepted by the normalizer when
  paired with a later revision assignment whose authored fields are aligned;
  and
- a complete embedded reconstruction of the Issue #7 revision-1..6 chain,
  with only revision 5 changed to omit `authorizedSlices` and every affected
  digest/context/link rebound, returns `[]` from full validation.

Exact row equality prevents this omission from deleting a non-empty accepted
Slice set, so this is Medium rather than High. It still turns post-compatibility
malformed history into accepted early history and contradicts the explicit
fail-closed compatibility boundary.

**Required remediation:** make compatibility selection depend on the exact
historical revision and, preferably, the explicitly recognized Issue #7
candidate/record lineage. Permit the legacy row form only for revision 1 and
the absent-`authorizedSlices` form only for revisions 2-4; reject them in
revision 5 and later. Add exact late-revision omission/legacy-shape negatives
while retaining the real revision-1 through revision-4 chain as positive
compatibility evidence.
