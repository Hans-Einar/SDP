### High

#### H-001 — Exact history does not bind the historical reservation row to the historical assignment

**Locations:** `SDP-vnext-pilot/ConcurrentAssignments.md`, especially the
repository-driver contract around lines 78-93;
`SDP-vnext-pilot/IssueContract.md`, especially lines 136-149;
`SDP-vnext-pilot/WorkflowContract.md`, lines 297-313; and
`SDP-vnext-pilot/validate_pilot.py`, especially `assignment_projection()` at
1943-1955 and historical loading/comparison at 2812-2912.

The seventh candidate correctly loads the exact historical assignment and
reservation bytes, strictly rejects duplicate/non-finite JSON, recomputes the
reservation digest, checks Issue/revision/source/base identity, requires one row
for the Issue, and compares immutable Issue/source/work/authorized-Slice
semantics across assignment revisions. It does not compare that one historical
reservation row with `assignment_projection(historical_assignment)`.

A fresh mutation started from the valid
`accepted-issue-reopen-revision.json` control, whose actual revision-1
assignment contains accepted `SLC-001@1010...`. In its exact embedded
revision-1 reservation bytes the probe removed `authorizedSlices`,
`activeSlices`, `reservedIds`, and `ownedPaths` from the Issue row. It then
recomputed the historical reservation digest
`sha256:15275a36ad5b58075e70ccc45d407dd62f430e27a57d0ef1dd47478cd46797b7`
and updated the exact historical assignment's digest, the typed snapshot, its
recorded context, and the current immediate-predecessor link. The exact
historical assignment still preserved accepted `SLC-001`; the reservation that
purportedly authorized it did not. Full `validate_document()` returned `[]`.

The committed tamper/digest-rewrite fixtures alter only one side and therefore
reject correctly. They do not exercise a self-consistent exact historical pair
whose row contradicts its assignment. Rehashing bytes proves integrity of those
bytes, not their semantic binding. This leaves the reusable accepted-Issue
reopen proof incomplete and reopens the core substance of `REV-006 H-002` for a
neighboring exact case.

**Required remediation:** after loading each exact historical reservation,
resolve exactly one canonical Issue row and compare its complete v0 projection
to the exact historical assignment. For earlier experimental bytes that predate
fields, define an explicit typed compatibility normalization rather than
silently accepting arbitrary row differences. At minimum preserve historical
Issue, primary work, authorized/active Slices and accepted candidates, reserved
IDs, owned/shared paths, dependencies and conflicts. Add coordinated-digest
negative controls for historical Slice deletion/candidate rewrite, work
replacement and path/ID removal inside the reservation row, not only in the
assignment bytes.

### Medium

#### M-001 — Reservation epoch identity is pair-based in prose but ID-only in resolution

**Locations:** `SDP-vnext-pilot/ConcurrentAssignments.md`, line 134 and the
current-epoch section; `SDP-vnext-pilot/IssueContract.md`, lines 145-151; and
`SDP-vnext-pilot/validate_pilot.py`, especially ID-only `by_id`/
`grouped_assignments` at 1961-2046, pair-based `epoch_key()` at 2220-2234,
ID-only repository materialization at 2961-2983, and ID-only fixture rebinding
at 3346-3357.

The normative pilot text says assignments are grouped by their bound
`(reservation-set ID, digest)`. That is also consistent with Issue #7 dogfood,
where the stable ID `RSV-ISSUE-007-001` is retained across six revisions while
the digest changes. `validate_assignments()` uses the documented pair.
`validate_reservation_sets()`, materialization, and the fixture rebind helper
instead index only by ID and reject/collapse more than one object carrying it.

A fresh probe started from the valid two-terminal-epoch control and retained
the distinct bases, rows, paths and digests while setting both reservation
objects to ID `RSV-010`. The two bound pairs were:

```text
(RSV-010, sha256:38be677e71aabb52add48efe2560bbf04d7cb6671a4fb8ccd5eebbda6bdbf436)
(RSV-010, sha256:f48c9ff2c6b54e677338628d64da18ed8c7b5e431123d7f0b33b74dd5e4b9136)
```

Both groups were terminal and independently complete. Validation returned
`RESERVATION_SET_INCOMPLETE` and `UNRESOLVED_RESERVATION_SET`, contradicting
the documented group identity. This matters when a stable coordination record
is refrozen and its terminal assignment evidence must coexist with a later
epoch without rewriting the earlier digest.

**Required remediation:** either implement `(ID, digest)` consistently in set
lookup, materialization and rebinding, with an unambiguous source/path rule, or
change the contract to make set IDs immutable one-digest identities and require
a fresh ID on every refreeze. The latter requires reconciling the current
dogfood/history narrative. Add a positive for two terminal epochs with one ID
and distinct digests, and negatives for a duplicate exact pair and an ambiguous
external path.

#### M-002 — Unreferenced reservation sets skip their own semantic validation

**Locations:** `SDP-vnext-pilot/ConcurrentAssignments.md`, reservation/refreeze
steps 1-5; `SDP-vnext-pilot/templates/reservation-set.template.json`; and
`SDP-vnext-pilot/validate_pilot.py`, especially the first-pass shape checks at
1958-2011 and the reference-group-only semantic loop at 2013-2195.

The protocol creates and publishes the shared reservation set before each
Master binds it. Every typed reservation object must therefore be independently
safe, even during that preparatory state. The validator checks the full base,
Issue graph, dependency DAG, complete merge order and terminal convergence only
for IDs referenced by an assignment.

A fresh probe appended an exact-marker reservation object that no assignment
referenced. It had `integrationBase: "not-a-sha"`, an Issue self-dependency,
empty merge order, blank owner/command, and `terminal: false`. Full validation
returned `[]`.

**Required remediation:** validate every typed reservation object independently
of assignment binding. Then compare each bound assignment group to the already
valid object. If pilot v0 intentionally permits a preparatory unbound set,
define that state and validate its complete rows/graph/gate; otherwise reject it
as orphaned. Add unbound invalid-base, self/cycle, order and convergence
fixtures plus a valid preparatory-set control if that lifecycle is retained.
