### High

#### H-001 — Work-owner delivery and implementation prerequisites are not evidence-closed

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, especially lines 37-49,
77-92, 148-153, 303-318; the Steering-accepted
`SDP-usage-analysis/ProposedSDPWorkflow.md` Feature and Slice completion rules;
and `SDP-vnext-pilot/validate_pilot.py`, especially lines 1306-1451 and
1880-1978.

The accepted synthesis says a Feature is delivered only when all required
Slices are accepted and its acceptance criteria are satisfied. The candidate
says `delivered` requires accepted implementation evidence and says Study
results need accepted authority before implementation. Validation checks that
a delivered Feature/Refactor has an Issue and at least one resolvable Slice,
but it does not require those Slices or their assignments to be accepted.

Fresh fully shaped mutations returned no diagnostic for each of these states:

- `FEAT-001` declared `delivered` with qualified Feature evidence while its
  `SLC-001` and Issue assignment were both changed to `active` with null
  evidence;
- the same Feature declared `released`, with a qualified Release reference,
  while the Slice and assignment remained active/unaccepted; and
- `SHARED-REF-001` declared `delivered` with qualified Refactor evidence while
  `SHARED-SLC-001` remained `proposed` and its assignment remained `active`.

A nearby prerequisite probe changed the accepted `HSX-STU-001` to `active`
with null evidence. The active Debugger Feature still had a `depends_on` edge
to that Study, and its active Slice still named the Study in `decisionRefs`;
validation returned `[]`. The prior accepted-assignment prerequisite fixture
correctly handles `dependsOnIssues`, but it does not close work/decision
prerequisites.

This can present incomplete implementation as delivered or released and can
authorize a Slice against an unaccepted decision. It is not the valid case
where an accepted assignment leaves a durable multi-assignment Feature
`active`; the false acceptance occurs at the work owner's terminal delivery/
release state or at Slice activation.

**Required remediation:** make the pilot completion/entry rule explicit and
validate it. A delivered/released Feature or Refactor must have every currently
represented required Slice accepted with qualified evidence and a coherent
accepted assignment; a non-standalone delivered Fix with Slices needs the same
closure. An active/accepted Slice's governing `decisionRefs` and retained
`depends_on` implementation prerequisites must resolve to evidence-qualified
accepted authority, or the contract must represent explicitly which relations
are non-gating. Preserve the valid active durable owner after one accepted
assignment. Add exact Feature, Refactor, Fix, released-work, and unaccepted-
decision fixtures.

#### H-002 — Missing schema markers are treated as an untyped escape hatch

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, lines 194-227;
`SDP-vnext-pilot/validate_pilot.py`, especially lines 495-645, 709-975,
1106-1225, 1249-1451, and 1511-1725.

The contract says every pilot v0 record, assignment, reservation set, registry,
and history snapshot uses its exact documented `schemaVersion`; unknown
markers are unsupported. The validator enforces that only after it has already
decided an object is typed. For records that decision is the presence of the
very `schemaVersion` field being required; for registries it is likewise
`strict_registry = "schemaVersion" in registry`. Reservation validation can be
downgraded by removing both `kind` and `schemaVersion` while retaining the
digest-bound content.

Fresh mutations demonstrated:

- removing only `schemaVersion` from the prospective `FEAT-001` returns `[]`;
- that schema-less Feature can claim `delivered` with null evidence while its
  Slice and assignment are unaccepted, and still returns `[]`;
- removing the Feature schema and replacing its qualified cross-domain target
  with bare `HSX-STU-001` returns `[]` because embedded semantic validation is
  skipped;
- removing only the registry schema marker returns `[]`; and
- removing `schemaVersion`, `kind`, and `experimental` from the reservation
  object, then rebinding its real digest, returns `[]`.

Keeping a schema marker and removing an ordinary required field correctly
emits required-field diagnostics, and changing a marker to an unknown value
correctly emits `UNSUPPORTED_SCHEMA_VERSION`. The failure is specifically a
missing-marker downgrade. Because the inventory says these are `prospective`
v0 identities rather than preserved legacy records, there is no legitimate
legacy ambiguity to justify silently skipping v0 semantics.

**Required remediation:** at the pilot-document/repository boundary, require
the exact schema marker, `kind`, and `experimental: true` for every prospective
record, active registry, current assignment/reservation set, and history
snapshot. If loose historical objects must remain inspectable, route them
through an explicit `legacy-preserved`/compatibility mode that cannot satisfy
current work, evidence, relation, reservation, or acceptance gates. Add missing
schema/kind/experimental fixtures for every v0 object kind, including combined
downgrade attempts.

### Medium

#### M-001 — Semantic edges allow circular authority and duplicate authored truth

**Locations:** `SDP-vnext-pilot/WorkflowContract.md`, lines 62-81 and 172-177;
`SDP-vnext-pilot/examples/scoped-monorepo.json`, the embedded
`DBG-FEAT-001 -> HSX-STU-001` edge and identical top-level relation; and
`SDP-vnext-pilot/validate_pilot.py`, lines 1228-1304 and 1454-1491.

The fourth candidate now rejects bare, unresolved, wrong-kind, invalid-type,
and same-list duplicate semantic edges. It does not reject circular self-
authority or normalize embedded and top-level edges into the one absolute
identity graph the contract describes.

Fresh probes returned `[]` for:

- `DBG-FEAT-001 depends_on DBG-FEAT-001`;
- `AVR-STU-001.independentStudyRefs` naming `AVR-STU-001` itself; and
- a delivered standalone zero-Slice Fix whose only `affectedWork` target was
  the Fix itself. Because the Fix was already declared delivered with evidence,
  it circularly satisfied the check intended to prove correction of previously
  accepted behavior.

The committed scoped positive example also contains the exact same
`depends_on` edge once inside the Feature and once in top-level `relations`.
Its normalized `(type, sourceRef, targetRef)` identities are equal, but the
validator keeps separate duplicate sets and returns `[]`; removing the
top-level copy also returns `[]`. A top-level edge additionally accepts an
ignored `candidate` extension while the identical field on an embedded edge
emits `INVALID_SEMANTIC_EDGE`, so the two authored surfaces have no consistent
extension/candidate contract.

**Required remediation:** choose one authored semantic-edge authority or define
one surface as a derived projection. Normalize duplicates across all retained
surfaces, reject semantically circular `depends_on`, self-independent Study,
and self-affected Fix edges, and state the extension/candidate-field policy
consistently. Add cross-surface duplicate, self-edge, and candidate/extension
controls.

### Low

#### L-001 — Surrogate paths cause an uncaught digest-encoding exception

**Locations:** `SDP-vnext-pilot/WorkDomains.md`, portable path rules;
`SDP-vnext-pilot/validate_pilot.py`, lines 169-185, 287-328, 1511-1725, and
2507-2517.

`normalize_path("src/a\\ud800b/**")` correctly returns invalid because `Cs` is
one of the explicitly forbidden Unicode categories. When that JSON-escaped
path exists in both an assignment and its reservation row, however,
`canonical_digest()` serializes with `ensure_ascii=False` and then UTF-8
encodes before the validation result can be returned. Both digest rebinding
and full `validate_document()` raise an uncaught `UnicodeEncodeError` instead
of producing `INVALID_PATH`/an invalid-digest diagnostic. This fails closed,
so it is Low rather than Medium, but it weakens deterministic actionable
validation of a category the contract expressly covers.

**Recommended remediation:** validate Unicode scalar/path safety before
canonical digest encoding and convert invalid UTF-8 scalar data into stable
diagnostics. Add an ASCII-escaped lone-surrogate fixture.

## Notes and limitations

1. Embedded-only validation accepts a strict registry with prospective
   inventory but zero represented records because the one-to-one check is
   guarded by `if record_list`. Repository-driver mode correctly emits
   `RECORD_INVENTORY_BINDING_MISMATCH`, and standalone registry templates need
   a non-materialized mode. The future interface should distinguish template,
   embedded scenario, and repository validation explicitly; this is not raised
   above Medium because the first real repository path fails closed.
2. Outer extension fields are accepted and preserved while strict nested
   evidence/embedded-edge shapes reject extras. That can be legitimate for a
   provisional format, but M-001 requires the two semantic-edge surfaces to
   state one consistent candidate/extension policy.
3. GitHub exposes repository activity primarily through `Hans-Einar`; fresh
   task context is process separation, not independently signed external actor
   provenance. Live GitHub/ref observations can change after this review.
4. This review did not run a real HSX migration, two live writing Issue
   Masters, a real repository move, or HSX product/platform tests. Those remain
   downstream pilot work after the contract itself has no unresolved
   Blocking/High/Medium finding.
