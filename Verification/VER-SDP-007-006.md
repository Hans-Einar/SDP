### High

#### H-001 — Preserved historical assignments are incorrectly treated as members of one current concurrent reservation set

**Locations:** WorkflowContract.md, especially the work-owner/Issue
cardinalities, reopen/extension rules, and terminal aggregate closure;
ConcurrentAssignments.md, especially the per-Issue preservation and
current-reservation rules; and validate_pilot.py, validate_assignments around
the global multi-assignment base/set/convergence checks and global path
collision accumulation.

The contract now correctly separates immutable ID allocation from later
execution authority and preserves each Issue's complete authorized-Slice
history. It also says per-Issue assignment records remain durable, a delivered
owner resolves every Issue authority to one preserved assignment, and a
reservation set contains every current concurrent assignment.

The validator does not distinguish preserved accepted history from the current
concurrent set. Whenever a document contains more than one assignment,
validate_assignments globally requires every assignment to have the same
integration base, the same reservation-set ID/digest, and the same convergence
contract. It also compares owned paths globally across all assignments,
regardless of whether they belong to different historical/current sets.

A fresh valid lifecycle probe demonstrated the defect:

1. Issue 10 and SLC-001 remain accepted under their immutable RSV-010,
   integration base A, evidence, and assignment record.
2. The durable Feature moves back to active and adds Issue 12 plus new SLC-002.
3. Issue 12 alone is the current RSV-012 assignment at later integration base
   B. Its active Slice has a null authorized candidate; the earlier accepted
   Slice retains its original candidate.
4. Both reservation objects are canonical and independently projection-bound.

Validation returned only CONVERGENCE_CONTRACT_MISMATCH and STALE_COMMON_BASE.
When the later sequential assignment legitimately reused an area written by
the already accepted predecessor, PATH_COLLISION was also returned.

The same false positive occurs after Issue 12 is accepted and the Feature is
terminal. Keeping both assignments in one set, as the positive two-Issue
fixture does, is not a general workaround: after the integration base advances,
moving the already accepted Issue 10 record into RSV-012/base B would rewrite
its durable accepted assignment terms. Omitting Issue 10 instead violates the
terminal rule that every work-owner Issue authority resolves to a preserved
assignment.

This is the remaining core continuation of the fifth-gate multi-Issue finding.
It prevents the contract from representing ordinary sequential Issue Masters
over changing integration bases, exactly the lifecycle the Issue and accepted
study require.

**Required rework:** distinguish preserved historical assignments from current
reservation membership. Validate common base, set, convergence, dependency,
conflict, and path collisions per current reservation-set group rather than
across every preserved assignment in the repository. Define a deterministic
current/historical discriminator without copying mutable GitHub state, retain
terminal owner resolution across historical assignments, and keep accepted
assignment bytes/evidence immutable. Add positive active and terminal controls
where Issue 10 remains under RSV-010/base A and Issue 12 uses RSV-012/base B,
including legitimate sequential path reuse; retain negatives for two genuinely
current sets, a current assignment omitted from its set, and concurrent path
overlap.
